# Décisions prises en autonomie

| # | Décision | Raison |
|---|---|---|
| D1 | Stripe Connect (déjà en place) remplace le formulaire IBAN en 4 étapes. Le RIB est saisi chez Stripe (identité, compte bancaire, justificatifs, statut « en cours de vérification / validé »). Aucun IBAN stocké ni affiché chez nous. | Exigence « IBAN jamais en clair » respectée par construction, moins de risque RGPD, pas de coffre à chiffrer. Versements toujours manuels. |
| D2 | Références : `ORG.` + 8 chiffres tirés avec `gen_random_bytes` (jamais séquentiels), index unique, boucle de relance en cas de collision ; `ADM.` idem sur `profiles`. Immuables (trigger qui refuse toute modification). | Anti-énumération. |
| D3 | Cycle de vie `en_attente → approuvé → suspendu` sur `organizers.account_status`. Les organisations existantes (THE MOUV) sont rétro-remplies en `approuvé`. Une organisation suspendue garde son accès en lecture mais ne peut plus rien publier ni vendre (appliqué côté serveur dès que les pages concernées existent). | Ne rien casser pour THE MOUV. |
| D4 | Nouveau CSS dans `app/organizer-shell.css` (importé par le layout organisateur), pas dans `globals.css`. | `globals.css` a des modifications non commitées d'une autre session. |
| D5 | Aucune nouvelle URL n'écrase une URL existante ; les pages actuelles (`/organisateur/participants`, etc.) restent servies. | « Ne casse aucune URL ». |
| D6 | Les migrations 010-013 restent à appliquer avant 014+. Je ne les applique pas sans `POSTGRES_URL_NON_POOLING`. | Base partagée. |
| D7 | Temps réel : (a) toute écriture du store ou de la billetterie appelle `revalidatePublicSite()` (`revalidateTag` + `revalidatePath('/', 'layout')`) ; les `revalidate = 60` des pages restent un simple filet de sécurité ; (b) stock public interrogé toutes les 2 s (cache CDN 1 s), en pause onglet masqué ; (c) tableau de bord d'évènement : sondage 2 s d'un point léger (`/live`, compteurs sans donnée personnelle), rechargement seulement si un chiffre change. | Supabase Realtime en `postgres_changes` exigerait des politiques RLS de lecture sur `tickets`/`orders` pour les membres d'organisation (aujourd'hui réservées au client et à l'admin) : je ne les ouvre pas sans validation. Le repli demandé (1-2 s, pause onglet masqué) est donc la solution retenue, sans canal à sécuriser. À reprendre avec des canaux Broadcast (sans donnée personnelle) si tu veux de l'instantané push. |
| D8 | En production, une modification de contenu éditorial (`/admin`) est un commit GitHub : la fiche publique est à jour au redéploiement qui suit (~1 min), pas avant, car le système de fichiers Vercel est en lecture seule. L'invalidation immédiate joue à plein pour tout ce qui est en base (billetterie, tarifs, stock). | Contrainte d'hébergement déjà documentée dans la mémoire du projet. |
| D9 | `next lint` n'est pas configuré dans ce dépôt (ESLint demande une configuration interactive) : les contrôles de phase sont `tsc --noEmit`, `next build`, `test:unit`, `test:db`. Je n'ajoute pas ESLint sans ton accord. | Ne pas modifier l'outillage sans besoin. |
| D10 | Entrées de menu non encore construites : affichées grisées avec la mention « Bientôt », non cliquables, jamais de page vide. Elles disparaissent au fil des phases. | Règle « zéro page vide déguisée ». |
| D11 | Les cases « viewer » du cahier n'existent plus : les rôles sont `owner / manager / staff` (migration 010). Un `staff` ne voit que Tableau de bord, Scan et le Centre d'aide. | Cohérence avec l'existant. |
| D12 | Vidéo du flyer : envoi direct navigateur → Vercel Blob (jeton serveur, formats et taille bornés), mesure et image d'aperçu faites dans le navigateur. Vidéo conforme (≤ 1080p, ≤ 60 i/s) : diffusée telle quelle (pas de ré-encodage). Vidéo 4K / > 60 i/s : enregistrée « Envoyée », l'affiche reste l'image ; la décision de transcodage (HEVC `libx265 -tag:v hvc1`, plafonds 1080p / 60 i/s, repli H.264 30 i/s) est écrite et testée dans `lib/videoRules.ts`, **mais aucun job ffmpeg ne tourne encore** (les fonctions Vercel n'embarquent pas ffmpeg de façon fiable ; un job externe gratuit type GitHub Actions est la voie, à brancher avec ton accord). | Ne pas promettre un traitement qui n'existe pas ; coût 0 €. |
| D13 | Lieux : coordonnées saisies (latitude / longitude) avec lien Google Maps généré ; pas de carte à marqueur déplaçable. | Une bibliothèque de carte ajoute une dépendance et des fournisseurs de tuiles : à décider. |
| D14 | Lineup côté organisateur : entrée « Bientôt ». Le lineup et les fiches artistes vivent dans le contenu éditorial (`data/content.json`, commit GitHub) réservé au panneau /admin ; l'ouvrir aux organisateurs demande une décision de migration. Le système existant (liens artistes, MAJUSCULES/gras, création auto) n'est pas modifié. | Ne pas régresser l'existant. |
| D15 | Texte des conditions par défaut = règlement du site, désormais dans `lib/rulesText.ts` (source unique de `/interdits`). Le rendu de `/interdits` reste identique. | Pas de duplication. |
